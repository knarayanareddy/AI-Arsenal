## Overview

Agentic Security is a Python package that installs as a console command and starts a local web interface on port 8718 for inspecting results. Attack surface is organised into suites: multimodal probes across text, image and audio; multi-step jailbreak sequences that iterate rather than firing once; general fuzzing with randomised inputs; and an API integration mode for pointing the scanner at a live service. There is also an RL-based attack mode that adapts probes in response to the target's defences. Datasets are plain CSV files with a prompt column loaded from disk on startup, which makes bringing your own corpus straightforward. A configuration file, generated by an init command, holds the target's request specification, a maximum budget, a failure threshold, an optimisation flag, and per-suite toggles such as whether multi-step simulation is enabled, with module sections naming the specific model and dataset each suite targets.

## Why It's in the Arsenal

The engineering problem is that adversarial testing of an LLM feature is a testing problem, not a research problem, and the friction is entirely in reproducibility. Running the same attack set on the same commit six months later is what tells you whether a guardrail change helped. Putting the target spec, the budget and the failure threshold in a checked-in config file means adversarial testing becomes a CI stage with a non-zero exit, the way a linter does. The cost is that you own interpretation: the scanner reports what a suite found, and a clean report is a statement about the suite rather than about the model.

## Key Features

- Target is a raw HTTP spec rather than a provider SDK, so any OpenAI-shaped or even non-OpenAI endpoint can be scanned without a code change.
- Multimodal and multi-step suites go beyond single-shot text jailbreaks, which is where most quick scanners stop.
- Budget ceiling and failure threshold are configuration, so a scan can run unattended in CI with a cost bound and a pass criterion.
- Apache-2.0 with bring-your-own CSV datasets, so you can test against your own domain content rather than a generic corpus.

## Architecture / How It Works

The CLI entry point boots a local HTTP server for the result UI, so scans have browsable output rather than only log output, and it accepts host and port flags for binding. Attack logic is split into modules, one per suite, with a config section per module controlling whether it runs and with what parameters; the documented sample config shows module keys named after the model and dataset they target. The target is described as a raw HTTP specification - method, URL, headers, and a JSON body containing a placeholder token that the attack prompt is substituted into - which means there is no per-provider SDK layer and any endpoint speaking that shape can be scanned, at the cost of writing the template yourself. Budget enforcement and the pass/fail threshold are evaluated across the run rather than per request, so a scan producing mostly-failing results does not necessarily abort early. A CI-oriented init step writes the config file, and the documented interface is the console command plus the local web view.

## Getting Started

Install the package and run the console command; it starts the local UI on its default port:

```bash
pip install agentic_security
agentic_security init   # writes a default config
agentic_security        # starts the scan server on port 8718
```

Point the config at your endpoint with a raw HTTP spec, drop CSVs with a prompt column next to it, and run agentic_security --port=PORT --host=HOST to rebind.

## Use Cases

1. Pre-release adversarial gate: point the config at your production-shaped endpoint with a failure threshold, and block a release when the scan exceeds it.
2. Guardrail regression check: run the same committed config against a candidate model and compare pass rates with the previous version.
3. Fuzz your own inference server: since the target is a raw HTTP template, use it against a self-hosted vLLM or llama-cpp endpoint and find inputs the serving stack mishandles.

## Strengths

It competes with garak in the LLM vulnerability scanner category, with the practical difference that garak is a broader research-oriented harness while this one is a compact package aimed at running a scan against an endpoint you operate. It overlaps with the red-team platforms in the same tools phase, such as AI-Infra-Guard, but those cover the surrounding infrastructure - MCP servers, skills, model fingerprints - whereas this targets the model or agent surface directly. Compared with ragas or deepeval, which measure quality and grounding, this produces adversarial outcomes rather than quality scores, so the two answer different questions about the same endpoint. It complements an agent framework rather than replacing one: it tells you whether the agent is exploitable, not how to build it.

## Limitations / When NOT to Use

A fuzzer is evidence, not assurance: the suites are finite, and a clean run says the model resisted what was tried rather than that it is safe. Detection depends entirely on which attacks the suite contains, so a model trained against public jailbreak benchmarks can look better than it is. Cost is a live variable - the budget mechanism exists precisely because fuzzing issues many calls, and an RL-based mode that adapts to your defences is by construction the expensive one. The package is small and lightly maintained, so expect interface churn and no vendor support. Integration is also manual where it matters most: you write the HTTP template yourself, and the README's section on adding LLM integration templates is marked as forthcoming, which means some provider setups are yours to build.

## Integration Patterns

This is the model-surface scanner in content/tools/evaluation-and-observability, and it is the narrowest of the security tools there because it stops at the API boundary.
