## Overview

utkuozdemir/nvidia_gpu_exporter is a dedicated Prometheus exporter written in Go that gathers operational metrics and telemetry from NVIDIA graphics processing units (GPUs). Built to support infrastructure observability across AI training, LLM inference, and graphics-intensive clusters, the tool exposes fine-grained hardware metrics over standard HTTP endpoints formatted for Prometheus scraping.

Architecturally, the exporter interfaces with the underlying GPU subsystem through two distinct execution modes: direct interaction with the NVIDIA Management Library (NVML) C-API or fallback parsing of XML output generated by the nvidia-smi CLI binary. NVML mode operates with minimal CPU and memory overhead by issuing direct Cgo calls to host libnvidia-ml.so, making it ideal for high-frequency polling. The fallback CLI mode provides compatibility in restricted security environments or non-standard container images where mounting host libraries is prohibited.

The collected metrics span critical hardware vectors including GPU compute utilization, memory usage (free, used, total VRAM), temperature thresholds, power draw against configurable watt limits, fan speeds, PCIe throughput (TX/RX bandwidth), ECC error counters, and clock frequencies (graphics, SM, and memory). This telemetry allows MLOps and SRE teams to set up real-time alerting on GPU thermal throttling, VRAM exhaustion during model loading, power capping degradation, and hardware faults.

## Why It's in the Arsenal

The exporter provides a lean, single-purpose alternative to heavy enterprise monitoring agents like NVIDIA DCGM (Data Center GPU Manager) Exporter. While DCGM requires complex host setup and higher system resource allocations, nvidia_gpu_exporter delivers standard compute and thermal metrics through a compiled, zero-dependency Go binary with minimal memory footprint.

A primary differentiator is its dual-driver telemetry strategy. In environments where dynamic loading of libnvidia-ml.so fails—such as tightly locked-down LXC containers or minimal Docker base images—the exporter smoothly degrades to running `nvidia-smi -q -x` to capture system state. This prevents complete metric collection outages during host-driver updates or container runtime discrepancies.

Furthermore, it allows explicit selection and dynamic filtering of monitored metric fields through CLI flags. Cluster operators can exclude volatile or irrelevant metrics to optimize Prometheus TSDB ingestion rates, reducing storage overhead when running large-scale multi-GPU fleets.

## Key Features

Dual Telemetry Engine: Interoperates via direct NVML dynamic linking (libnvidia-ml.so) for low latency or CLI parsing via `nvidia-smi` when library binding is unavailable.

Prometheus Standard Formatting: Exposes standard OpenMetrics/Prometheus gauge and counter metrics over standard HTTP endpoints (default `:9835/metrics`).

Granular Field Filtering: Exposes flags such as `--web.telemetry-path` and dynamic query flags to selectively include or drop specific metric categories (e.g., power, clocks, compute utilization, memory, ECC, PCIe).

Basic Auth & TLS Support: Integrates Prometheus web-config specs, enabling native TLS encryption and basic HTTP authentication directly within the exporter server process.

Container & Bare-Metal Compatibility: Distributes as a standalone static binary or lightweight OCI image for deployment as a DaemonSet in Kubernetes or a systemd service on bare-metal GPU nodes.

## Trade-offs

Lacks Advanced Profiling & MIG Features: Does not natively support fine-grained NVIDIA DCGM features such as Multi-Instance GPU (MIG) slice-level profiling, enterprise health checks, or advanced hardware diagnostic suites.

NVML Dynamic Linking Overheads: When compiled with Cgo for NVML mode, host glibc and driver library path alignment is required, which can lead to runtime startup failures if libnvidia-ml.so is not correctly mounted into the container.

Subprocess Overhead in Fallback Mode: Running in `nvidia-smi` CLI mode spawns a child process per scrape interval, causing spikes in host CPU usage and latency when scraped at high frequencies (e.g., under 1 second).
